# Research log for worldwide trip planning

Last reviewed: 2026-09-26. Record only project-relevant source facts and design decisions here; do not store user searches, personal data, or large third-party datasets.

## City lookup

- 2026-09-27 live local-browser query through the existing [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) and its [public usage policy](https://operations.osmfoundation.org/policies/nominatim/): an explicitly clicked `Paris, France` city search returned three visually identical Paris candidates, with some region/country labels containing semicolon-separated language aliases. Decision: collapse only same-name, same-region/country, within-5-km duplicates for display and show a single alias; preserve distant namesakes. This does not expand request volume. Public Nominatim still has a 1-request/second aggregate policy, no autocomplete/bulk use, and no production availability promise; client caching/throttling remains local-only. No user query history or bulk response data is stored here.

- 2026-09-26 recheck: [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) documents `featureType=city` as an address-layer filter, `addressdetails=1` for location labels, and free-form `q` for a place name. [JSON output fields](https://nominatim.org/release-docs/develop/api/Output/) include OSM identifiers and coordinates. The [public policy](https://operations.osmfoundation.org/policies/nominatim/) still limits aggregate traffic to at most 1 request/second and forbids autocomplete and bulk searches. Decision: use this only as an explicitly clicked, cached local-prototype fallback when Open-Meteo fails; do not silently generate a second request or claim public-production readiness. In live testing the primary Paris search recovered, so no live Nominatim city response was claimed.
- Source: [Open-Meteo Geocoding API](https://open-meteo.com/en/docs/geocoding-api). It supports global location-name searches and returns candidate coordinates and region/country labels. Use it to disambiguate cities; a typed string alone is not a selected destination.
- Limitation: [Open-Meteo terms](https://open-meteo.com/en/terms) say the free API is for non-commercial use, rate-limited, and has no availability guarantee. A public/commercial release needs a suitable licensed provider or self-hosted alternative.
- Decision: keep lookup user-triggered and separate from POI lookup.

## Place discovery

- 2026-09-26 sources: official [Nominatim Lookup API](https://nominatim.org/release-docs/develop/api/Lookup/), [output format](https://nominatim.org/release-docs/develop/api/Output/), and [public usage policy](https://operations.osmfoundation.org/policies/nominatim/). Lookup accepts an OSM object ID prefixed with `N`, `W`, or `R` and can return its coordinates, names and extra tags. The public endpoint limits the entire application to at most one request per second, requires caching/attribution and identification, and disallows autocomplete or systematic harvesting. Decision: add only a single explicit user-pasted OSM object lookup, reject unsupported/nonlocal results, reuse session caching and client throttle, and never claim this is production-ready aggregate rate enforcement. Live local-browser check: Eiffel Tower OSM way `5013364` resolved to a source-linked Paris place and entered a one-day itinerary. This fallback does not provide live opening/price/transit data, nor make worldwide search complete.

- 2026-09-26 review: OpenStreetMap's [amenity key](https://wiki.openstreetmap.org/wiki/Key:amenity), [shop key](https://wiki.openstreetmap.org/wiki/Key:shop), and [tourism key](https://wiki.openstreetmap.org/wiki/Key:tourism) document restaurant/cafe/food-court/market, mall/department-store, zoo/theme-park and other feature types. Decision: in the existing bounded nearby Overpass request, include a small 3-km food/shopping sample; preserve a few of those categories when trimming results; and score `美食`, `購物`, `親子` only from matching OSM types. These tags do not establish taste, price, opening hours, age suitability, accessibility or quality, so recommendation reasons explicitly require verification. This adds no additional request, but the shared Overpass endpoint may still time out. A live Paris named search returned a source-linked cafe and the UI correctly explained the food-category match before placing it in a one-day trip.

- 2026-09-26 recheck: the official [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) documents `viewbox` as a result bias and `bounded=1` as a hard boundary; the [public endpoint policy](https://operations.osmfoundation.org/policies/nominatim/) still requires low-volume, cached, identified, non-autocomplete use and forbids systematic POI harvesting. Decision: offer a separate wider lookup only after the user explicitly requests it, keep the city-centered viewbox, locally reject results beyond 120 km, and cache both scopes. This can improve recall but does not prove complete coverage. The earlier failed Fushimi Inari query was not assumed to be fixed; live retesting remains open. A direct response inspection through the web tool was inaccessible, so no unsupported claim about that POI is recorded.
- 2026-09-26 repeat local-browser lookup under the same [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) and [usage policy](https://operations.osmfoundation.org/policies/nominatim/): Paris landmark candidates remained source-linked and selectable while testing itinerary editing. No new provider capability or licensing assumption was adopted; earlier limits still apply. The session draft stores only the chosen places needed to restore the local trip, not a bulk third-party catalog.
- 2026-09-26 live check using the same [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) and [public usage policy](https://operations.osmfoundation.org/policies/nominatim/): a deliberate Rome landmark query returned a source-linked Colosseum feature before the separate Overpass nearby request completed. Decision: make the user-triggered named lookup immediately accessible after city choice; keep the broader nearby call optional/background. This improves perceived reliability without sending extra systematic queries. The public endpoint still has the low-volume/no-production limitations recorded below.
- 2026-09-26 live prototype check (same [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) and [public usage policy](https://operations.osmfoundation.org/policies/nominatim/) below): explicit Kyoto landmark queries returned Kiyomizu-dera, Nijo Castle, and Kyoto Imperial Palace, but the tested Fushimi Inari variants returned no matching candidate. This shows that bounded public name search is incomplete and alias-sensitive. Decision: keep a truthful no-result state and source-linked user selection; do not silently fabricate a replacement or launch automated query expansion against the shared endpoint. No private query history or bulk result data is retained here.
- 2026-09-26 source: [Nominatim public usage policy](https://operations.osmfoundation.org/policies/nominatim/). The shared endpoint requires an identifying Referer/User-Agent, OSM attribution, a maximum of 1 request/second for the entire application, caching, and a readily replaceable provider. It disallows autocomplete and systematic/bulk POI harvesting. This prototype uses only a deliberate named-place submit, a browser-session cache and a 1.1-second client throttle. Client throttling cannot enforce a global limit across users, so this public endpoint is suitable only for low-volume local evaluation; a published app needs an alternative provider or self-hosted instance.
- 2026-09-26 sources: [Nominatim Search API](https://nominatim.org/release-docs/develop/api/Search/) and [result fields](https://nominatim.org/release-docs/latest/api/Output/). A bounded `viewbox` with `bounded=1`, `q`, and `limit=8` supports an explicit named-place lookup near a selected city. Returned OSM type/ID and coordinates can be linked to the source, but a name search is not a complete POI catalog or proof of opening hours or visitor suitability. Decision: let the user add a returned place as a candidate, with a verification caveat, rather than inventing missing destinations.

- Source: [OSM tourism tags](https://wiki.openstreetmap.org/wiki/Key:tourism) and [Overpass API guidance](https://wiki.openstreetmap.org/wiki/Overpass_API). OSM features may include categories, names, coordinates and optional access/fee/opening tags. These fields are not uniformly present or verified.
- Limitation: public Overpass instances are shared resources for small projects, can be overloaded, and ask apps to cache and rate-limit requests; their usage policy counts all app users together. Do not use the public endpoint as an unrestricted production search backend.
- Decision: score only evidence the app actually retrieved. The first explainable matching rules cover `自然` with park/viewpoint and `深度` with historic/cultural categories. Do not claim that OSM categories prove a place is romantic, child-friendly, uncrowded, inexpensive, or open on a chosen date.
- Next investigation: user-controlled nearby/name/category search and a bounded query strategy that discovers requested locations without broad scraping; evaluate provider terms before public deployment.

## Road-route evidence

- 2026-09-26 sources: [FOSSGIS routing-server information and policy excerpt](https://routing.openstreetmap.de/about.html), [OSRM route HTTP API](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md), and [OSRM frontend endpoint conventions](https://github.com/Project-OSRM/osrm-frontend). The public service offers road-network distance/time from coordinates and asks for attribution, a valid referrer, at most 1 request/second, and no scraping/heavy use. It records route requests in its server logs and gives no production availability guarantee. Decision: a user may explicitly check one leg's car road time; the browser caches the small result for 24 hours and throttles requests, but does not auto-query every leg. This is separate from transit schedules, taxis, fares and live traffic. The browser successfully returned about 4.0 km and 10 minutes for a Paris Louvre-to-Eiffel road leg while the prior distance-model vehicle choice showed a different estimate. No route result or user query history is committed. A deployed multi-user app requires its own quota-enforcing backend or suitable provider; per-tab throttling cannot enforce an aggregate limit.
